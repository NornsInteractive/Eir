# 项目开发原则

适用范围：整个 App、服务端、构建脚本及后续平台实现。以下为项目约束，不局限于第一版。

## 1. 开发前先确认能否复用

每次开发功能或逻辑前，先检查仓库现有实现与已安装依赖，再查验 Flutter/Dart 或目标平台的标准能力，以及现存成熟库。先评估再动手，不默认自研。

选择顺序：现有项目能力 → 标准库/平台能力 → 已安装依赖 → 适合的成熟库 → 必要的自定义实现。能直接复用就直接复用，避免同一职责维护多套方案。

成熟度按实际需要判断：功能匹配、目标平台支持、维护情况、稳定 API、许可证、安全风险、体积和性能。不能仅凭下载量引入，也不为几行清晰的标准库逻辑增加依赖。

新引入依赖或决定自研时，在对应设计或变更说明中简要记录候选、选择原因和已知限制；无需为每个小改动另建长篇选型文档。复用已评估方案时只需确认当前需求仍满足。

## 2. 少封装、少抽象

- 直接使用框架或库的正常接口，不为每个库再包一层 service、manager、repository 或 facade。
- 仅在真实业务规则、平台差异或实际复用需要时增加最小适配；不能以“未来可能替换”为由预建通用接口。
- 已有组件、工具函数、模型和设计语义直接复用；相同逻辑只维护一份，但不要把仅外形相似的不同业务强行合并。
- 不自研已有成熟方案的播放器、网络穿透、密码算法、本地化或基础组件体系；业务特有的同步与授权规则仍需明确实现和验证。
- 选择成熟库不等于省略信任边界校验、错误处理、可访问性和必要测试。

## 3. 外观扩展与业务分离

遵循 [App 外观与主题要求](APP-SETTINGS.md)。主题和外观变体复用业务状态、播放会话、权限与同步逻辑，不复制整套业务实现。

第一版使用框架原生主题、组件样式和必要的少量自定义语义；后续遇到实际外观变体时再添加所需结构。不要提前构建皮肤引擎、远程代码加载、主题市场或多层插件框架。

## 4. 完成检查

提交前确认：已检查可复用能力；依赖选择有依据；没有重复职责和无用转发封装；测试覆盖实际新增风险；文档准确说明限制。检验标准是满足需求且易维护，不是文件数或代码行数。

## 5. 默认跨平台支持

没有特定平台要求或明确范围例外时，每个业务功能默认支持 Windows、macOS、Linux、Android、iOS、Web，不需要用户逐项重复提出跨平台要求。该约束覆盖界面、业务逻辑、数据存储、文件访问、网络、多语言、主题和其他应用功能。

- 设计、依赖选择、实现与验收从一开始覆盖目标平台，不采用默认只完成开发机平台、其他端以后再考虑的方式。
- 优先复用跨平台成熟库和共享逻辑；实际平台差异使用最小必要适配，不复制整套业务或增加无用途的封装。
- Flutter 能构建或依赖标注支持，不等于功能可用；需验证所用 API、权限、编解码、浏览器限制、生命周期及输入布局。
- 平台无法提供相同能力时，优先寻找替代实现；确实受限则明确说明受影响平台、原因及降级行为。不得静默省略、使用空实现或把未验证写为已支持；需要缩减需求时交由用户确认。
- 交付说明按平台区分已验证、未验证和明确受限，未具备设备/环境时如实记录验证缺口。
- 明确的平台专属功能或已确认的阶段性交付范围可作为例外，例外应在需求中记录；不能把开发者自行作出的范围假设当作用户特定要求。

用户现已确认首版六端并授权执行计划，原桌面先行假设不再适用。实际验证结果应逐端记录，不能把六端目标写作六端已完成。
