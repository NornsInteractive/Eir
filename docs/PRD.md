# 异地同步观影应用：设计需求文档（PRD）

版本：v0.1　状态：待确认

## 1. 产品概述

一款跨平台（Windows / macOS / Linux / Android / iOS / Web）的异地同步观影应用。多人（3-10 人）进入同一房间，**同步观看同一视频**，进度实时共享。

核心设计原则：

1. **服务端极轻**：只提供信令（握手）服务，视频数据不经过服务器，靠设备间 P2P 传输。
2. **谁有视频谁供片**：URL 视频各自拉取；本地视频由添加者作为数据源，其他成员边收边播，并互相转发。
3. **权限由人定、角色由系统选**：房主和管理员由人指定，负责控制播放；"谁来协调、谁来供片"由系统按设备能力自动选择。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 房主（Owner） | 创建房间的人，唯一，拥有最高权限 |
| 管理员（Admin） | 房主指定，可控制播放和编辑播放列表 |
| 成员（Member） | 其余人，只能观看 |
| 条目（Item） | 播放列表中的一个视频 |
| Leader | 系统自动选出的协调者（必须是房主或管理员），负责给控制指令排序并提供时间基准，用户无感知 |
| Seeder | 持有视频数据并向他人供片的设备；本地视频的添加者是初始 Seeder，已缓存的成员自动成为 Seeder |
| 信令服务 | 仅用于交换连接信息的轻量服务，不接触视频内容 |
| NAT 打洞 | 让位于不同路由器后面的两台设备建立直接连接的技术 |
| STUN / TURN / ICE | STUN 帮设备查询公网地址；TURN 在打洞失败时中继数据；ICE 是自动尝试各种连接路径并选出最优的流程 |
| Mesh（全连接） | 房间内每两位成员之间都有一条直连 |

## 5. 设备连接方案

### 5.1 总体思路

多台设备通过"**信令服务牵线 + WebRTC 直连**"组网：

1. 设备先连上信令服务，在同一个房间里互相"认识"（交换连接信息）。
2. 随后设备两两之间通过 NAT 打洞建立 **P2P 直连**。之后所有数据（控制指令、同步状态、视频片段）都走这条直连，不再经过服务器。
3. 直连打不通的少数情况，自动降级到中继。

选用 WebRTC 作为唯一传输方式：它是浏览器里唯一能做 UDP 打洞的技术，因此 Web、手机、桌面可以用同一套协议互通，并且自带加密（DTLS）。

### 5.2 连接架构

```
                 ┌──────────────────────┐
                 │   信令服务（WSS）      │  只交换连接信息，不接触视频
                 └──────▲────▲────▲─────┘
                        │    │    │
                 ┌──────┘    │    └──────┐
                 │           │           │
              设备 A ◄────► 设备 B ◄────► 设备 C
                 ▲                       ▲
                 └────── P2P 直连 ────────┘      （3-10 人两两直连）

   STUN：帮设备查询自己的公网地址，辅助打洞
   TURN：打洞失败时的中继，兜底使用，限速限时
```

### 5.3 组件职责

| 组件 | 做什么 | 不做什么 |
|---|---|---|
| 信令服务（WebSocket） | 房间登记与成员发现；转发连接信息（SDP、ICE 候选）；校验邀请凭证；下发 STUN/TURN 配置与临时凭证；直连失败时中继少量已签名的控制消息 | 不接触视频内容；不保存播放状态；不能伪造控制指令 |
| STUN 服务 | 告诉设备自己的公网 IP 和端口 | 不转发任何数据 |
| TURN 服务（coturn） | 直连失败时中继数据 | 不作为默认路径；限速、限时 |

### 5.4 加入房间的连接流程

1. **解析邀请链接**：链接包含房间号、信令服务地址和一次性邀请凭证。
2. **连接信令服务**：设备通过 WSS 连接，并用设备密钥签名完成身份认证。
3. **加入房间**：信令服务校验邀请凭证和人数上限，返回当前在线成员列表以及 STUN/TURN 配置，同时通知房内其他成员"有人加入"。
4. **逐个建立 P2P 连接**：新成员与房内每位成员各建立一条连接。为避免两边同时发起冲突，约定 **设备 ID 较小的一方发起连接**。
5. **收集并交换候选地址（ICE）**：双方通过信令服务交换本机地址、公网映射地址（STUN）、中继地址（TURN），并自动尝试连通性检测，选出最优路径。
6. **建立数据通道**：每对设备之间固定建立 3 条通道：`ctrl`（控制与同步消息）、`data-urgent`（紧急片段）、`data-bulk`（预取片段）。
7. **身份握手**：双方用设备密钥对"本次连接的 DTLS 指纹 + 随机数"签名并互验，确认对方正是自己看到的那个身份，**防止信令服务被攻破后做中间人**。验证邀请凭证；被封禁者拒绝。
8. **同步房间状态**：新成员从已有成员处获取最新的权限列表、播放列表和播放状态（带签名，可验证），并估算与 Leader 的时钟偏差。
9. **开始预取与播放**：按播放列表预取视频片段，进入同步播放。

### 5.5 组网拓扑

- 3-10 人采用**全连接（Mesh）**：任意两人之间直连，10 人最多 45 条连接。
- 控制指令和同步消息由发出者直接发送给所有人，无需经过第三方转发。
- 视频片段由 Swarm 机制在成员间调度：谁有就从谁那里取，不要求"必须从数据源取"。
- 与信令服务的 WebSocket 连接在整个房间生命周期内保持，用于新成员加入、成员重连和兜底中继；**信令服务断开不影响已建立的 P2P 连接和播放**。

### 5.6 连接路径与自动降级

连接路径由 ICE 自动选择，按下表优先级尝试：

| 优先级 | 路径 | 说明 | 数据是否经过服务器 |
|---|---|---|---|
| 1 | 局域网 / 同一公网出口直连 | 两台设备在同一网络 | 否 |
| 2 | IPv6 直连 | 家宽 IPv6 无需 NAT，成功率高 | 否 |
| 3 | STUN 打洞（UDP） | 覆盖大多数家用路由器 | 否 |
| 4 | UPnP / NAT-PMP 端口映射 | 桌面端主动在路由器开端口（M4） | 否 |
| 5 | 经其他成员转发 | 设备 C 连不上 A，但能连上 B，则片段从 B 取 | 否 |
| 6 | TURN 中继 | 打洞失败的最后手段，限速限时（M3） | 是 |
| 7 | 信令服务中继 | 只中继体积很小、已签名的控制消息，保证控制通路不断；不传视频 | 是 |

**要求**：路径 1-3 自动完成；路径 5 由分片调度自然支持；路径 6、7 仅在直连失败时启用，界面需明确提示该成员当前"通过中继连接"。

### 5.7 不同网络环境下的预期

| 网络组合 | 预期结果 |
|---|---|
| 同局域网 / 双方 IPv6 | 直连，几乎 100% |
| 锥形 NAT ↔ 锥形 NAT（常见家用路由器） | STUN 打洞成功率高（约 90%） |
| 锥形 NAT ↔ 对称 NAT | 成功率较低，常需 TURN |
| 对称 NAT ↔ 对称 NAT（运营商级 NAT、部分移动网络、校园网、企业网） | 基本只能 TURN |

以上为经验估计，实际以测试数据为准。产品目标：直连成功率 ≥ 85%，含兜底后 ≥ 98%。

### 5.8 断线与重连

| 场景 | 行为 |
|---|---|
| 单条 P2P 连接断开 | 自动重连，最多 3 次，间隔 1、2、4 秒；仍失败则尝试 TURN；再失败则标记该成员"不可达"，其片段与消息改由其他路径获取 |
| 成员掉线超过 10 秒 | 视为暂时离开，保留其席位和权限；重新连入后自动恢复 |
| 信令服务断开 | 客户端自动重连；期间已建立的连接和播放不受影响；仅新成员无法加入 |
| 信令服务重启（房间数据丢失） | 房主或管理员重连后自动重新登记房间，其他成员随后重连 |
| 手机切后台或网络切换（Wi-Fi ↔ 蜂窝） | 回到前台或网络恢复后，自动重新建立连接并快速对齐播放状态 |
| 房主或管理员全部离线 | 已建立的连接保持，房间进入自走模式 |

### 5.9 连接状态展示

成员列表中，每位成员显示：连接类型（直连 / 中继 / 不可达）、延迟（RTT）、缓冲状态。用户据此判断谁的网络有问题，也作为系统自动选源的依据。

### 5.11 部署需求

| 组件 | 要求 |
|---|---|
| 信令服务 | 公网可访问，仅 WSS（TLS）；1 核 1 GB 可支撑约 2000 个房间；房间信息仅存内存，重启后由房主或管理员重新登记即可恢复；有连接频率、房间数、消息大小限流 |

## 6. 关键用户流程

**6.1 创建并邀请**
房主创建房间 → 获得邀请链接 → 发送给朋友 → 朋友点击链接加入，几秒内看到当前播放列表与播放状态。

**6.2 添加 URL 视频**
管理员粘贴 URL → 客户端探测时长并校验可播放 → 加入播放列表 → 所有成员各自从 URL 拉取并按房间时间播放。

**6.3 添加本地视频**
管理员选择本地文件 → 客户端分析格式：
- 已是 H.264 / AAC：直接切片（几乎不耗 CPU，保持原画质）
- 其他格式：转码为 H.264 / AAC（优先硬件编码）

→ 生成视频清单并广播条目 → 其他成员开始预取 → 缓冲达到开播条件后即可开始播放，边播边继续下载。

**6.4 同步控制**
管理员暂停、拖进度、倍速 → 指令经 Leader 排序后广播 → 所有人在约 1 秒内一致响应。成员在界面上看到的是"只读"的播放控制条。

**6.5 授权管理员**
房主在成员列表中点击"设为管理员" → 全体成员收到并验证房主签名的授权更新 → 该成员获得控制权限。撤销同理。

**6.6 异常情况**
- 某成员网络卡顿：本人显示缓冲状态；若开启"等待所有人"，全房间暂停等待
- Leader 掉线：系统自动在在线的房主 / 管理员中重新选出，播放不中断
- 数据源掉线：已缓存该内容的成员继续供片；若无人有完整缓存，缺失部分提示"数据源离线"
- 没有任何房主或管理员在线：进入自走模式，按当前状态继续播放，当前条目结束后自动播放下一条，期间无人可控

## 7. 非功能需求

| 类别 | 指标 |
|---|---|
| 同步精度 | 稳态下 P95 播放位置偏差 ≤ 150 ms |
| 操作响应 | 管理员操作到全员生效 ≤ 1 s（已缓冲的情况下） |
| 加入速度 | 点击邀请链接到看到房间状态 ≤ 3 s |
| 连接成功率 | 不借助 TURN 的直连成功率目标 ≥ 85%；含 TURN 与信令中继兜底后 ≥ 98% |
| 开播等待 | 本地视频添加完成后，达到预取阈值（默认 10-30 秒缓冲）即可开播 |
| 资源占用 | 免转码场景下，数据源 CPU 占用单核 < 15%；客户端核心内存 < 300 MB |
| 信令服务 | 1 核 1 GB 机器可支撑约 2000 个房间同时在线 |
| 安全 | 所有 P2P 通信加密；控制指令签名可验证；片段逐片哈希校验 |
| 隐私 | 服务器不保存视频内容；成员的 IP 对其他成员可见（P2P 固有特性），需在隐私政策中说明 |

## 8. 限制与约束

**规模**：单房间默认上限 10 人（可配置到 12）；管理员上限 8；播放列表上限 200 条。

**平台能力**：

| 平台 | 可当房主 / 管理员 | 可当 Leader | 可当主要数据源 | 可当观众 |
|---|---|---|---|---|
| 桌面（Win / macOS / Linux） | ✅ | ✅ | ✅（首选） | ✅ |
| Android | ✅ | 仅前台 | 视网络和电量而定 | ✅ |
| iOS | ✅ | 仅前台 | ❌（后台会被挂起） | ✅ |
| Web | ✅ | 仅前台 | 仅限已兼容格式 | ✅ |

**视频格式**：P2P 分发统一使用 H.264 + AAC 的分片 MP4。HEVC / AV1 / VP9 等需要转码，仅桌面端支持转码。DRM 保护内容（如 Netflix）无法分发，也不支持。

**依赖**：数据源设备需保持在线；无数据源在线时，未缓存的部分无法播放。

## 9. 里程碑范围

| 里程碑 | 目标 | 范围 |
|---|---|---|
| **M1** 核心验证 | 桌面端两人跑通完整链路 | F-01 ~ F-09：创建与加入、角色与签名权限、URL 与本地（H.264/AAC）视频、同步播放、基础播放列表。Leader 固定为房主。连接：信令服务 + STUN 打洞直连、断线重连（F-29）、身份握手 |
| **M2** 多人与分发 | 3-10 人可用 | F-10 ~ F-15、F-28：全连接组网、连接状态展示、Swarm 互助、预取与预热、转码、等待所有人、踢人 |
| **M3** 自动化与多端 | 自动选择角色，扩展平台 | F-16 ~ F-21：能力探测与自动选源、Leader 选举、自走模式、Web 与移动端观众、TURN 与信令中继兜底（C-10、C-11）、加入审批、延迟补偿 |
| **M4** 健壮性与增强 | 提升体验与稳定性 | F-22 ~ F-27：房主转让、主机接力、UPnP 与 IPv6、URL 兜底、嵌入源、聊天 |

## 10. 非目标

- 不做视频平台，不托管、不存储用户视频内容
- 不提供屏幕共享、语音通话（可作为未来扩展）
- 不支持 DRM 内容
- 不做账号体系与社交关系链（身份基于设备密钥，房间靠邀请链接）
- 不保证在所有网络环境下 P2P 直连成功，极端情况依赖 TURN 中继

## 11. 验收总则

每个里程碑的验收必须包含：

1. **功能验收**：该阶段所有功能项的用户流程可在真实设备上走通
2. **指标验收**：满足第 7 节中对应的性能与精度指标
3. **异常验收**：模拟弱网（丢包、高延迟）、成员掉线、Leader 掉线、数据源掉线，系统行为符合第 6.6 节
4. **安全验收**：非授权成员伪造控制指令被所有客户端拒绝；篡改的视频片段被丢弃并不再信任该来源
5. **自动化**：核心逻辑（同步、权限验证、分片调度）有可自动运行的单元与集成测试，CI 通过
6. **连接验收**：在以下网络组合下实测连接成功率与降级行为——同局域网、双方家宽（不同运营商）、一方移动网络、一方校园网或企业网、IPv6 对 IPv4；并验证信令服务中途断开、成员 Wi-Fi 切换蜂窝时播放不中断或可快速恢复
